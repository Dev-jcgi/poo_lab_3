Enum type

Simulador de despliegue táctico

Una unidad de fuerzas especiales simula duelos individuales entre soldados. Cada soldado tiene una especialidad y un rango, y el duelo lo gana quien tenga mayor nivel de autoridad.

Punto de partida: leé el modelo

Especialidad.java ya está resuelto. Antes de escribir una línea, abrilo y fijate en tres cosas: el punto y coma después de la última constante, que el constructor no lleva public, y que el atributo es final. 
public enum Especialidad {

    INFANTERIA("INF"),
    MEDICO("MED"),
    INGENIERO("ING"),
    FRANCOTIRADOR("FRA");   // <-- punto y coma OBLIGATORIO

    private final String sigla;

    Especialidad(String sigla) {   // constructor implícitamente privado
        this.sigla = sigla;
    }

    public String getSigla() { return sigla; }
}

Preguntas de comprensión

?¿Qué error da new Especialidad("XYZ") y por qué es bueno que falle?
Pista para pensarlo: ¿cuántas instancias de Especialidad deberían existir en todo el programa? ¿Qué pasaría si cualquiera pudiera fabricar una quinta especialidad en tiempo de ejecución? Probalo en el código y leé el mensaje del compilador.
?¿Por qué guardar el nivel como atributo del enum en vez de resolverlo con un switch?
Imaginá que mañana agregan el rango CORONEL. Con el atributo, agregás una línea. Con el switch, tenés que acordarte de actualizar todos los switch del proyecto — y si te olvidás de uno, el compilador no te avisa.
?¿Qué problema traería agregarle un setRango() a Soldado?
Pensá en el momento del duelo: si dos partes del programa tienen una referencia al mismo soldado y una lo modifica en medio de la comparación, el resultado deja de ser predecible. La inmutabilidad elimina esa clase entera de errores.
?¿Qué hace ordinal() y qué riesgo tiene apoyarse en él?
Investigalo en la documentación. Después preguntate: ¿qué pasa con tu programa si alguien reordena alfabéticamente las constantes del enum? Con getNivelAutoridad() no pasa nada; con ordinal(), la lógica se rompe en silencio.

Clases abstractas · Interfaces

Red social de creadores de contenido

Todos los creadores comparten atributos comunes (seguidores, energía, popularidad), pero cada nicho tiene habilidades distintas. Esa diferencia es exactamente la que separa una clase abstracta de una interfaz.

La idea central de esta actividad. Lo que todos son va en la clase abstracta (Creador: nombre, seguidores, energía). Lo que solo algunos pueden hacer va en interfaces (IColaboracion, IPromocion, IModeracion).

Quién puede hacer qué

                 IColaboracion   IPromocion   IModeracion
  Gamer               ✔               ✔             —
  Vlogger             ✔               —             ✔
  Educador            —               ✔             ✔
Java no permite heredar de dos clases. Un Gamer no puede extends Creador y Promotor a la vez. Pero sí puede implementar todas las interfaces que necesite. Esa es la forma en que Java resuelve lo que en otros lenguajes sería herencia múltiple — y es el motivo de que esta actividad exista.

Punto de partida: leé el modelo

public class Gamer extends Creador implements IColaboracion, IPromocion {
        //          └── UNA sola clase ──┘        └── VARIAS interfaces ──┘

    @Override
    public void publicarContenido() { ... }   // viene de la clase abstracta

    @Override
    public void hacerFeat(Creador otro) { ... }  // viene de IColaboracion

    @Override
    public void anunciarProducto(Creador[] audiencia) { ... }  // viene de IPromocion
}

Preguntas de comprensión

?¿Qué error da new Creador("test") y por qué está bien que falle?
Probalo en el Main. Después preguntate: ¿qué debería hacer publicarContenido() en un creador "genérico"? No hay respuesta razonable — y por eso la clase es abstracta: representa un concepto, no algo que exista.
?¿Por qué los atributos van en la clase abstracta y las habilidades en interfaces?
Preguntate qué pasaría si hacerFeat() estuviera dentro de Creador: el Educador quedaría obligado a tener un método que, según el enunciado, no debería poder usar. Las interfaces permiten que cada tipo tenga solo las habilidades que le corresponden.
?¿Por qué simularEventoPromocion recibe IPromocion y no Gamer?
Esta es la pregunta más importante de la actividad. Al pedir "algo que sepa promocionar" en vez de "un Gamer", el método funciona igual con Gamer, con Educador, y con cualquier clase futura que implemente la interfaz — sin tocar una línea de este método.
?En gestionarAgenda(), ¿por qué no alcanza con escribir creador.hacerFeat(otro)?
Probalo y leé el error. El parámetro está declarado como Creador, y esa clase no conoce hacerFeat(). El compilador solo te deja llamar a lo que el tipo declarado garantiza. Ahí entra instanceof + casteo.
Sobre la defensa oral. Las preguntas de esta guía son las mismas que pueden hacerte en la defensa en vivo. No hay sorpresa: si podés responderlas mirando tu código, estás listo. Si tu programa funciona pero no podés explicar por qué escribiste una línea, esa línea no suma.
